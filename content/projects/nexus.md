## 담당 영역

저는 팀장으로서 본사 **발주 관리**, **실시간 알림**, **매출 통계 집계** 세 도메인과 배포 인프라를 담당했습니다. 발주와 알림은 SCM의 일상 업무가 흐르는 기능이고, 통계는 그 결과를 집계하는 시스템입니다. 두 기능을 먼저 정리하고, 가장 깊게 파고들었던 통계 시스템의 8단계 고도화를 이어서 다룹니다.

### 발주 관리 - 마감과 동시에 AI가 발주서 초안을 만든다

가맹점 점주가 하루 영업을 마감하면, 그 시점의 **재고 현황과 재고 변동 이력, 과거 발주 이력, 요일 정보**를 모아 프롬프트를 구성하고 **Spring AI ChatClient로 GPT-4o를 호출**해 품목별 발주 수량을 제안받습니다. 응답은 JSON으로만 받도록 제약해 파싱을 안정화했고, 생성된 발주서는 AUTO·WAITING 상태로 저장돼 본사 발주 관리 페이지의 **자동 발주 제안 목록**에 올라갑니다. 본사는 이를 검토해 승인하거나 수정합니다.

![자동 발주 제안 흐름 - POS 마감 → 데이터 수집·프롬프트 구성 → GPT-4o 수량 제안 → AUTO·WAITING 저장 → 본사 검토·승인](images/projects/nexus/auto-order-flow.svg)

구현에서 두 가지 선택이 있었습니다. LLM 호출을 별도 Python 서비스로 빼는 대신 **Spring AI를 채택**한 것은 팀 전원이 Java를 쓰는 상황에서 학습 비용과 운영 부담을 최소화하기 위해서였고, temperature를 0.3으로 낮춘 것은 발주서가 정확한 수량이 중요한 문서라 같은 재고 상태에서 매번 다른 추천이 나오면 안 되기 때문입니다. 금요일과 토요일 마감에는 주말 배송 불가를 프롬프트에 함께 알려, 월요일까지 버틸 수량을 고려해 제안하도록 했습니다.

이 발주서들이 모이는 본사 발주 관리 페이지는 자동 발주 제안, 확정 발주, 발주 이력, 이상 발주 네 가지 목록을 검색 조건과 페이징으로 조회합니다. 네 메서드 모두 Specification 기반 동적 쿼리였는데, DTO 변환에서 매장 이름에 접근할 때마다 Store가 개별 조회돼 **10건 조회에 쿼리 11회**가 나가는 N+1이 있었습니다.

해결 방법은 네 가지를 비교했습니다. JPQL JOIN FETCH는 Specification의 동적 조건을 포기해야 하고(조건 조합별 쿼리가 최대 16가지), @BatchSize는 쿼리가 줄어들 뿐 사라지지 않으며, 전역 batch_fetch_size는 세밀한 제어가 어렵습니다. 네 메서드 모두 항상 매장 이름이 필요한 to-one 연관이라, Repository의 findAll을 **@EntityGraph로 오버라이드**해 한 줄로 네 메서드를 전부 해결했습니다. TalleMalle에서는 컬렉션 N+1이라 @BatchSize를 골랐지만 여기서는 동적 쿼리와의 호환이 우선이었습니다. **같은 N+1이라도 연관의 모양과 쿼리 방식에 따라 처방이 다릅니다.** 목록 외에 상세 조회, 일괄 승인, 이상 발주 재평가까지 다섯 지점을 정리해 쿼리 수 기준 11회 → 1회, 21회 → 2회 수준으로 줄였습니다.

### 실시간 알림 - 알림에는 WebSocket이 아니라 SSE

발주 상태가 바뀌면 관련 화면에 즉시 알림이 떠야 했습니다. TalleMalle에서는 채팅이라는 양방향 요구 때문에 WebSocket(STOMP)을 선택했지만, 알림은 **서버에서 클라이언트로 흐르는 단방향**입니다. 양방향 프로토콜을 깔 이유가 없고, SSE는 HTTP 위에서 그대로 동작해 인프라 추가가 없으며 브라우저가 재연결을 자동으로 처리합니다. 그래서 EventSource 구독과 브로드캐스트 구조의 **SSE 알림을 직접 구현**했습니다. 알림이 저장되는 순간 연결된 클라이언트에 곧바로 push되는 구조입니다. 같은 실시간이라도 통신의 방향이 기술을 결정한다는 것을, 두 프로젝트에서 서로 다른 선택을 해 보며 체득했습니다.

## 통계 집계 시스템 - 가장 깊게 파고든 문제

결제가 발생할 때마다 본사·가맹점의 매출 통계를 집계하는 시스템입니다. 초기 구조는 결제와 통계가 **같은 애플리케이션, 같은 DB**를 쓰는 모놀리식이었습니다. 결제가 진행되는 동안 통계 조회가 함께 들어오는 실제 사용 상황을 k6로 재현하자(결제 램핑 최대 100 VU + 통계 폴링 5 VU · 5분), **결제 응답 p95가 3.5초, 통계 응답 p95가 1.97초**까지 밀렸습니다. 결제 트랜잭션의 행 잠금과 통계의 집계 쿼리가 한정된 커넥션 풀을 두고 경합한 결과였고, 핵심 흐름인 결제가 파생 작업인 통계에 발목 잡히는 구조라는 것을 수치로 확인했습니다. 그래서 **통계 기능을 MSA로 분리**하기로 결정했습니다.

![출발점 - 결제·통계·기타 도메인이 한 애플리케이션과 한 DB를 공유하는 모놀리식 구조](images/projects/nexus/arch-monolith.png)

먼저 통계 서비스를 별도 애플리케이션과 별도 DB로 분리했습니다. 다만 **한 번에 변수 하나**라는 원칙에 따라, 이 단계에서는 요청 경로를 옮기지 않고 모든 요청이 여전히 모놀리식으로 향하게 둔 채 같은 부하 테스트만 다시 돌렸습니다. 결과는 결제 p95 5.29초, 통계 p95 2.84초. 구조를 나누기만 해서는 아무것도 나아지지 않는다는 것을 확인하고, 이 수치를 이후 단계를 비교할 기준선으로 삼았습니다.

![1단계 분리 - Statistics MSA와 별도 DB를 준비했지만, 요청은 아직 전부 모놀리식으로 향하는 상태](images/projects/nexus/arch-msa-prep.png)

분리된 통계 DB는 모놀리식 DB에 쌓이는 결제·매장·메뉴 데이터를 받아와야 합니다. 두 DB 사이의 **데이터 정합성**을 맞추기 위해, 변경을 도메인 이벤트로 발행하고 통계 MSA의 Consumer가 구독해 적재하는 **Kafka를 도입**했습니다.

![Kafka 도입 - 모놀리식은 도메인 이벤트를 발행만 하고, Statistics MSA의 Consumer가 구독해 별도 DB에 집계하는 구조](images/projects/nexus/arch-kafka-msa.png)

이 구조로 부하 테스트를 돌리자 **세 가지 문제가 한꺼번에 드러났습니다.**

- 결제 성공은 6,529건인데 Kafka 발행은 6,533건 - DB에 없는 결제가 메시지로 존재하는 **유령 메시지 4건**
- 통계 DB에는 5,899건만 반영 - **600여 건의 데이터 증발**
- 발행 피크는 초당 약 22건인데 Consumer 처리량은 약 3건 - 밀린 메시지를 따라잡는 데 **회복 약 40분**

이 문제들을 차례로 해결한 기록이 아래 트러블슈팅 1·2입니다. 매 단계 같은 k6 시나리오(동시 100 VU · 5분, 시드 데이터 기준)를 반복해 변경 하나의 효과만 분리해서 측정했습니다.

### 트러블슈팅 1. 결제보다 많은 메시지 - 커밋 전 발행이 만든 유령 4건

#### 문제 상황

세 문제 중 가장 먼저 추적한 것은 유령 메시지였습니다. 결제 성공은 **6,529건**인데 Kafka 발행은 **6,533건**. DB에 존재하지 않는 결제가 메시지로는 4건 존재하는 **유령 메시지**(phantom)가 발생한 것입니다.

![1차 부하 직후 pos.payment.created 토픽 - Message Count 6,533 (결제 성공 6,529건과 4건 불일치)](images/projects/nexus/kafka-topic-6533.png)

#### 원인 분석

원인은 발행 시점이었습니다. `@Transactional` 메서드 안에서 `kafkaTemplate.send()`를 호출하면 **DB 커밋 전에 메시지가 브로커에 도달**할 수 있습니다. 이후 트랜잭션이 롤백되면 DB에서는 결제가 사라지지만, 이미 떠난 메시지는 회수할 수 없습니다.

#### 해결 과정

발행 시점을 옮기는 방법으로는 세 가지를 비교했습니다. Outbox 패턴은 별도 테이블과 폴링 워커가 필요하고, Kafka 트랜잭션(XA)은 운영 복잡도가 커서, 클래스 한두 개 추가로 문제의 대부분을 해결하는 **AFTER_COMMIT 리스너**를 선택했습니다. 결제 로직은 Spring Event만 발행하고, 실제 Kafka 발행은 **커밋이 확정된 뒤에만** 수행되도록 분리했습니다.

```java
// 결제 서비스 - 트랜잭션 안에서는 스프링 이벤트만 발행
@Transactional
public void pay(...) {
    // DB INSERT ...
    eventPublisher.publishEvent(new PaymentCreatedEvent(...));
}

// 별도 Publisher 컴포넌트 - 커밋 성공 이후에만 Kafka로 발행
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onPaymentCreated(PaymentCreatedEvent e) {
    kafkaTemplate.send("pos.payment.created", e.getStoreIdx(), e.getPayload());
}
```

리스너를 결제 서비스 클래스 안에 두면 같은 클래스 내부 호출이 프록시를 우회해 리스너가 조용히 무시되는 함정이 있어, 발행은 **별도 Publisher 컴포넌트로 분리**했습니다. 덕분에 결제 서비스는 Kafka의 존재 자체를 모르게 됐습니다. 다만 이 방식도 커밋이 성공한 뒤 Kafka 전송이 실패하는 반대 방향의 빈틈은 막지 못합니다. 이 잔여 위험은 현재 부하 수준에서 의식적으로 수용했고, 규모가 커지면 Outbox 패턴으로 보완할 지점으로 기록해 뒀습니다.

#### 결과

부하 테스트 전에 존재하지 않는 메뉴 번호로 결제를 강제 실패시키는 단건 테스트부터 돌렸습니다. 응답은 400, 결제 테이블 카운트는 그대로, Kafka에는 새 메시지가 없었습니다. 롤백 시 발행이 일어나지 않는 것을 확인한 뒤 부하 테스트로 넘어갔고, 재측정에서 Kafka 발행과 결제 INSERT가 **4,055 = 4,055로 정확히 일치**했습니다. 유령 메시지는 **4건 → 0건**, 롤백된 트랜잭션의 메시지가 밖으로 흘러나가는 일이 구조적으로 차단됐습니다.

![2차 k6 - 결제 성공 4,055건, AFTER_COMMIT 적용 후 Kafka 발행 건수와 일치 (결제 p95는 9.32초로 아직 악화 중 - 4차에서 해결)](images/projects/nexus/k6-round2.png)

### 트러블슈팅 2. 통계에서 사라진 600여 건 - 데이터로 바로잡은 오진

#### 문제 상황

유령 메시지와 같은 1차 부하에서 소비 쪽 수치도 맞지 않았습니다. Kafka 발행은 6,533건인데 통계 DB에는 **5,899건만 반영**돼, 600건이 넘는 집계가 사라진 것으로 추정됐습니다. 처리 속도도 문제였습니다. 모니터링상 발행 피크는 초당 약 22건인데 Consumer 처리량은 약 3건. Pod 하나가 파티션 3개를 단독 점유한 채 직렬로 소비하느라, 부하가 끝난 뒤 밀린 메시지(LAG)를 따라잡는 데 **약 40분**이 걸렸습니다. 2차 부하의 회복 중 스냅샷에서도 파티션별 LAG가 342, 0, 597로 쌓여 있는 것이 확인됐습니다.

![1차 부하 직후 Consumer 현황 - Active Consumer 1개에 처리 못 한 Lag 6,026건이 밀려 있는 상태](images/projects/nexus/kafka-consumer-1pod.png)

![1차 부하 20분 뒤 Grafana - 소비 속도가 초당 3건에 묶인 채 Consumer Lag 수백 건이 계단식으로 남아 있는 모습](images/projects/nexus/grafana-consumer-lag.png)

#### 원인 추적 - 진단을 번복하다

처음에는 누락을 Consumer 쪽 경쟁 상태로 진단하고 트러블슈팅 문서까지 작성했습니다. 그런데 2차 부하의 회복 완료 시점에 재측정하니 **누락이 0건**이었습니다. 경쟁 상태가 원인이라면 2차에서도 재현됐어야 합니다. 다시 추적한 결과, 1차의 누락은 통계 DB에 잘못 남아 있던 모놀리식 스키마 잔재와 Pod가 재시작될 때마다 시드 데이터가 다시 적재되는 설정이 겹친 **환경 문제**일 가능성이 높다고 결론 내렸고, 경쟁 상태라는 처음의 진단은 오진으로 확정해 바로잡았습니다. 진단은 번복했지만, 그 과정에서 설계한 멱등 Consumer와 DLQ는 메시지 교차 도착 대비와 실패 가시성이라는 **별도의 가치가 있다고 판단해 계획대로 적용**했습니다.

#### 해결 과정

**① 멱등 Consumer** - 같은 메시지를 두 번 처리해도 결과가 같도록 만들되, 도메인 특성에 따라 다르게 적용했습니다. 결제는 PK가 매번 새로 발급돼 충돌 자체가 비정상이므로 존재 확인 후 건너뛰며 로그를 남기고, 매장·메뉴는 created와 updated 메시지가 교차 도착할 수 있으므로 DB가 한 쿼리 안에서 원자적으로 흡수하도록 `ON DUPLICATE KEY UPDATE`를 썼습니다. `INSERT IGNORE`는 먼저 도착한 메시지만 살아남아 최신 정보가 유실될 수 있어 배제했습니다.

```sql
-- 매장·메뉴 동기화: 신규든 중복이든 한 쿼리로 원자 흡수
INSERT INTO store (store_idx, store_name, ...)
VALUES (...)
ON DUPLICATE KEY UPDATE store_name = VALUES(store_name), ...
```

**② DLQ** - DLQ는 실패를 처리하는 장치라기보다 **실패를 보이게 만드는 장치**라고 판단했습니다. 기본 에러 핸들러가 재시도 끝에 메시지를 건너뛰고 offset을 커밋하면, LAG는 0인데 DB에는 없는 영구 누락이 모니터링에 잡히지 않습니다. `DeadLetterPublishingRecoverer` + `FixedBackOff`(1초 간격 3회 재시도)로 실패 메시지를 `.DLT` 토픽에 격리하고, 격리 시 원본 파티션 번호를 유지해 같은 매장 메시지의 순서를 추적할 수 있게 했습니다.

**③ Consumer 스케일아웃** - replicas 증설, 파티션 수 확대, concurrency 설정, bulk insert 네 가지를 비교했습니다. 파티션 3개 환경에서는 **replicas 3으로 파티션과 1:1 매핑**하는 것이 가장 직접적이었고, concurrency 3은 당장은 노는 스레드지만 파티션을 늘릴 때 코드 변경 없이 따라 확장되는 보험이라 함께 적용했습니다. 파티션 키는 같은 매장의 처리 순서가 보장되도록 storeIdx로 잡되, 메뉴는 본사 전역 리소스라 storeIdx 필드 자체가 없어 menu 토픽만 menuIdx를 키로 썼습니다.

#### 결과

- 3차 재측정에서 Kafka 발행과 DB INSERT가 **3,562 = 3,562**로 일치, 측정상 누락 0건
- 재시도로도 처리 못 해 DLT에 격리된 메시지 **0건** (토픽이 생성조차 되지 않음)
- LAG 회복 시간 **약 40분 → 2~3분** (약 90% 단축)

### 성능 개선 여정 - 모놀리식 동기 집계에서 Redis Cluster까지 8단계

위 두 트러블슈팅을 포함한 전체 여정을 단계별로 정리하면 다음과 같습니다. 매 단계 같은 조건으로 측정해 다음 병목을 찾는 방식이었고, 그 과정에는 **가설이 빗나간 단계**도 있었습니다.

| 단계 | 변경 | 효과 |
|------|------|------|
| 기준 | 모놀리식 동기 집계 | 결제 p95 3.5초 · 통계 p95 1.97초 |
| 1차 | Kafka 이벤트 발행·소비 도입 | 유령 4건·누락·회복 40분 발견 (결제 p95 4.0초) |
| 2차 | AFTER_COMMIT 발행 + 파티션 키 | 유령 메시지 0건, 매장별 순서 보장 |
| 3차 | 멱등 Consumer + DLQ + 3 Pod | 측정상 누락 0건, 회복 40분 → 2~3분 |
| 4차 | 통계 조회를 독립 MSA로 라우팅 | 결제 p95 14.9초 → 2.74초 · 통계 → 189ms |
| 5차 | Redis 사전 집계 도입 | 통계 API 응답 균일화 (대가: 회복 약 20분) |
| 6차 | Redis 중심 구조 (집계 경로의 DB 쓰기 제거) | 회복 20분 → 14분 (가설 미달) |
| 7차 | Redis Pipeline (메시지당 왕복 약 15회 → 2회) | 회복 약 2분 |
| 8차 | Redis Cluster (Master 3 + Replica 3) | 단일 장애점(SPOF) 해소 |

**4차**

정합성은 좋아지는데 결제 p95는 4.0초, 9.3초, 14.9초로 부하를 돌릴 때마다 악화됐습니다. Consumer 쪽 변경이 모놀리식 응답을 느리게 만들 이유는 없으니, 결제와 통계가 같은 DB와 CPU를 경합한다는 가설을 세웠습니다. 통계 조회 경로만 독립 서비스로 돌리자 결제 p95가 **14.9초에서 2.74초로** 떨어지며 가설이 입증됐고, 통계 p95도 189ms로 함께 개선됐습니다. 라우팅 분리는 부담을 옮기는 게 아니라 **경합을 제거해 양쪽을 모두 살리는 변경**이었습니다.

![4차 k6 실측 - 라우팅 분리 직후 결제 p95 2.74초, 통계 p95 188.9ms](images/projects/nexus/k6-round4.png)

**5차**

결제 이벤트 수신 시점에 Redis 자료구조에 미리 집계해 두고 조회를 O(1) 읽기로 바꾸자, 126ms에서 401ms까지 벌어져 있던 통계 6개 API의 p95가 **94~133ms로 균일하게 수렴**했습니다. 무거운 쿼리일수록 효과가 컸습니다. 대신 메시지 1건당 Redis 명령이 10여 개 늘면서 Consumer 회복 시간이 약 20분으로 악화되는 대가를 치렀고, 이 트레이드오프가 6차와 7차의 출발점이 됐습니다.

![5차 k6 - Redis 사전 집계 적용 후 통계 응답이 100ms 안팎으로 수렴 (sales/today p95 132.99ms)](images/projects/nexus/k6-round5.png)

**6차·7차**

회복 20분의 원인을 메시지당 DB INSERT로 보고 6차에서 집계 경로의 DB 쓰기를 제거했습니다. 가설은 3~5분이었는데 실측은 14분, 미달이었습니다. 다시 분석하니 병목은 명령 개수가 아니라 **명령마다 발생하는 네트워크 왕복**이었습니다. Redis 연산 자체는 마이크로초 단위인데 왕복은 밀리초 단위였기 때문입니다. 7차에서 집계 명령을 Pipeline으로 한 번에 묶어 메시지당 왕복을 약 15회에서 2회로 줄이자 Consumer 처리량이 초당 약 21건에서 약 150건으로 늘고 **회복 시간은 약 2분**이 됐습니다. 반환값으로 중복 여부를 분기해야 하는 멱등성 확인 1회만 Pipeline 밖에 단일 명령으로 남겼습니다.

### 검증 실험 - 통계 저장소를 비우고 Kafka 로그로 다시 만들기

집계 경로에서 DB 쓰기를 제거(6차)하려면 한 가지 질문에 답이 필요했습니다. **통계 저장소가 날아가면 어떻게 복구하는가.** 마침 앞서 멘토 제안으로 진행했던 복구 실험이 이 질문의 답이 되어 주었습니다. Kafka에 원천 이벤트가 보존돼 있다면 통계 저장소는 언제든 다시 만들 수 있는 파생 상태라는 가설의 검증이었습니다.

통계 DB의 부하 데이터를 비우고(시드 30,000건은 유지), Consumer의 offset을 earliest로 되돌리고, Pod를 재시작했습니다. DB를 직접 복구하는 명령은 **0회**였습니다. Consumer는 보존된 메시지 **18,376건을 약 18분에 걸쳐 재생**했고, 시드 데이터와 겹치는 3,969건은 멱등성 장치가 정확히 건너뛰었으며, 중복 INSERT와 DLT 격리는 모두 0건이었습니다. 손실 전 상태로 되돌린 복구가 아니라, **Kafka 로그로부터 파생 상태를 재생산**한 것입니다.

이 실험이 있었기에 6차에서 Redis 영속화에 의존하지 않고 Kafka를 안전망으로 삼는 결정을 내릴 수 있었습니다. 동시에 이 방식은 통계처럼 다시 만들 수 있는 파생 데이터에 적합할 뿐, 결제 같은 원천 데이터에는 쓸 수 없다는 적용 경계도 함께 정리했습니다.

### 기술 선택: 통계 저장소를 왜 Redis로, 왜 Cluster로 갔나

**왜 집계 갱신을 이벤트로 했나** - 조회 시점에 DB를 SUM하는 대신 결제 시점에 미리 더해 두기로 하면서, 갱신 경로를 두 가지와 비교했습니다. 결제 트랜잭션 안에서 Redis까지 갱신하는 Write-Through는 Redis 장애가 결제 실패로 전파되고, 주기 배치는 실시간성이 죽습니다. 이미 깔아 둔 Kafka 이벤트를 Consumer가 구독해 갱신하면 결제와 완전히 분리되면서 실시간성도 유지돼 이 길을 선택했습니다.

**자료구조를 도메인에 맞게** - 합계 카운터는 String INCRBY, 매장·메뉴 랭킹은 정렬을 자료구조가 대신해 주는 Sorted Set ZINCRBY(TOP5 조회가 O(log N)), 시간대·결제수단 분류는 Hash HINCRBY로 매핑했습니다. 집계 쿼리를 자료구조 연산으로 옮긴 것이 5차 응답 균일화의 본질이었습니다.

**왜 영속화를 끄고도 불안하지 않았나** - 위 복구 실험으로 Kafka 로그가 안전망이 된다는 것을 먼저 확인했기 때문입니다. Redis가 데이터를 잃어도 replay로 다시 만들 수 있으니, 저장소 영속화는 이중 안전망이라고 판단했습니다.

**왜 Cluster인가** - 매 결제가 쓰기인 패턴이라 읽기 복제만 늘리는 Sentinel 구성으로는 부족했고, 무엇보다 Redis 한 대가 죽으면 통계 조회 전체가 멈추는 단일 장애점과 수직 확장만 가능한 단일 노드의 메모리 한계가 문제였습니다. 가용성 확보와 학습을 겸해 **Master 3 + Replica 3 클러스터를 의식적으로 선택**했고, 그 대가로 키가 슬롯별로 분산되며 통계 p95가 95ms에서 154ms로 늘어나는 것을 수용했습니다. 16,384개 해시 슬롯이 마스터 3대에 균등 분배되고 실제 키 분포도 편차 0.1% 이내임을 확인했으며, 의외로 결제 p95는 250ms에서 193ms로 오히려 개선됐습니다. Redis 부하가 3노드로 분산된 영향으로 추정하고 있습니다.

클러스터 도입 전에는 VM 환경에서 장애 상황을 직접 재현해 봤습니다. Master 하나를 강제로 내리자 잠시 뒤 Replica가 Master로 승격됐고, 데이터가 유실되지 않았으며, 죽었던 노드를 다시 올리자 Slave로 클러스터에 합류하는 것까지 확인했습니다.

![Redis Cluster 장애 재현 - 다운됐던 Master(10.10.10.11)가 재기동 후 Slave로 클러스터에 합류한 cluster nodes 출력](images/projects/nexus/redis-failover.png)

### 무중단 배포 - Blue/Green 슬롯 전환 검증

본사와 가맹점이 업무 시간 내내 사용하는 B2B 서비스라 **배포 중단은 곧 업무 마비**로 이어집니다. Kubernetes 위에 Blue/Green 두 슬롯을 두고 새 버전을 대기 슬롯에 올린 뒤 트래픽을 전환하는 방식으로 무중단 배포를 구성했습니다. 전환 중 0.1초 간격으로 반복 호출한 curl에서 **502·503 응답은 0건**이었고, 프론트엔드 화면에 현재 슬롯명을 표시해 전환 시점을 눈으로도 확인했습니다.
